# เริ่มตรงนี้

[English](START-HERE.md) · **ภาษาไทย**

![เริ่มตรงนี้](assets/start-here.png)

ถ้าคุณ vibecode — บอกว่าอยากได้อะไร ให้ AI เขียนให้ แล้วส่งขึ้นจริง — หน้านี้เขียนให้คุณ
ไม่ต้องรู้ว่า STRIDE คืออะไร ไม่ต้องอ่านเอกสารอื่นมาก่อน สิบห้านาที แล้วคุณจะได้ใช้มันจริง

---

## ปัญหาที่มันแก้

คุณเคยเจอแน่ๆ AI บอกว่า:

> "แก้ให้แล้วครับ ตอนนี้ปุ่มทำงานถูกต้องแล้ว"

แล้วมันไม่ทำงาน หรือทำงาน แต่มีอย่างอื่นห่างออกไปสามไฟล์พังเงียบๆ หรือมันบอกว่า
"เทสต์ผ่าน" ทั้งที่ไม่เคยรันเทสต์ คุณไม่ได้โกหกตัวเอง — AI บอกคุณว่าเสร็จแล้ว
เป็นประโยคเต็ม น้ำเสียงมั่นใจ

นั่นไม่ใช่โมเดลห่วย แต่คือโมเดล **รายงานเจตนาของตัวเองแทนที่จะรายงานความจริง**
ซึ่งเป็นเรื่องที่พลาดง่ายมากเมื่อไม่มีอะไรมาบังคับให้แยกสองอย่างนี้ออกจากกัน

ตัวอย่างจริงจากโปรเจกต์ต้นทาง มีช่องหนึ่งที่แยก URL แล้วมันไปตัดด้วยตัวอักษร `s`
เพราะ backslash หายไปตัวเดียวใน regular expression มันอยู่บน production
และ **มันไม่เคยทำงานถูกเลยแม้แต่ครั้งเดียว** ตั้งแต่วันที่เขียนมันขึ้นมา ไม่มีใครเห็นเป็นเดือน
เพราะเวลามันพัง อาการมันดูเหมือน *เว็บอีกฝั่ง* ล่ม

อ่านโค้ดยังไงก็ไม่เจอ มีแต่การรันจริงเท่านั้นที่เจอ

เพราะงั้นแนวคิดทั้งหมดของที่นี่คือประโยคเดียว:

> **ยังไม่นับว่าเสร็จ จนกว่าจะตรวจในที่ที่คำว่า "เสร็จ" เป็นจริง**

บอกว่า "ขึ้นบนหน้าเว็บแล้ว"? ก็ไปดูหน้าเว็บ บอกว่า "บันทึกแล้ว"? ก็อ่านแถวนั้นกลับออกมาจาก
ฐานข้อมูล บอกว่า "build ผ่าน"? ก็รัน build แล้วแปะสิ่งที่มันพิมพ์ออกมา ไม่ใช่โค้ด ไม่ใช่แผน
แต่คือตัวมันเอง

แค่นั้น ทุกอย่างที่เหลือในรีโปนี้คือแนวคิดเดียวกันนี้ เอาไปใช้กับงานแต่ละแบบ

## ติดตั้ง (2 นาที)

```
/plugin marketplace add neckttiie090520/nzs-skills
/plugin install nzs-skills@nzs-skills
```

ถ้าตอนติดตั้งขึ้นว่า `Run /reload-plugins to activate` ก็สั่งตามนั้น

**เช็กว่าติดจริง** พิมพ์ `/` แล้วต้องเห็น `nzs-start` ในรายการ ถ้าไม่เห็น แปลว่ายังไม่ติด
ดูที่หัวข้อ [ถ้ามันไม่ทำงาน](#ถ้ามันไม่ทำงาน)

---

## ใช้จริงครั้งแรก (10 นาที)

ไม่ต้องไปไล่อ่านรายการ skill แค่ถาม:

```
/nzs-start อยากเพิ่มหน้า login ให้แอป
```

คุณจะได้ **แผนว่าจะใช้ skill ไหนบ้าง เรียงยังไง** และที่สำคัญที่สุดคือ เส้นชัยที่ใครก็ตรวจได้
ประมาณนี้:

```
ประเภทงาน: build

Stack:
  1. method-plan      ซอยเป็น milestone พร้อมวิธีตรวจของแต่ละอัน
  2. method-code      เขียน ทีละ milestone
  3. method-security  งานนี้แตะ credential เพราะงั้นข้อนี้ไม่ใช่ตัวเลือก
  4. method-verify    พิสูจน์ก่อนจะเรียกว่าเสร็จ

ไม่อยู่ใน stack: method-research — คุณไม่ได้ก๊อปดีไซน์ใคร

เสร็จเมื่อ: login ในเบราว์เซอร์ด้วยผู้ใช้จริงได้ และ login เป็น user A แล้วอ่านข้อมูล
ของ user B ไม่ได้ (พิสูจน์ด้วย request จริง ไม่ใช่ด้วยการอ่านโค้ด)
```

สังเกตสิ่งที่มัน **ไม่** ทำ: มันไม่ยื่นตัวเลือกสิบอันมาให้คุณเลือกเอง router ที่ยื่นเมนูให้
คือ router ที่โยนการตัดสินใจกลับมาให้คุณ ซึ่งเป็นสิ่งที่คุณขอให้มันช่วยตัดสินใจตั้งแต่แรก

จากนั้นแค่บอกว่า **"เอาเลย"** แล้วปล่อยให้มันไล่ทำตาม stack

## สิ่งที่คุณจะรู้สึกว่าต่าง

**มันเถียงกับตัวเอง** `method-review` จะไล่โค้ดคุณหลายรอบ แต่ละรอบสวมหมวกคนละใบ —
รอบหนึ่งล่าเฉพาะช่องโหว่ความปลอดภัย รอบหนึ่งล่าเฉพาะเคสสุดขอบ รอบหนึ่งอ่านแบบคนแปลกหน้า
หมวกแต่ละใบเห็นสิ่งที่ใบอื่นมองไม่เห็นเชิงโครงสร้าง และทุกรอบจะเริ่มด้วยการตรวจว่าของที่
รอบก่อนแก้ *ลงจริงไหม* เพราะในโปรเจกต์ต้นทางมีสามรอบแยกกันที่จับได้ว่าการแก้ถูกรายงาน
ว่าเสร็จทั้งที่ไม่เคยเกิดขึ้น

**มันไม่ยอมพูดว่า "เสร็จ" ถ้าไม่มีอะไรให้ดู** ถ้าพิสูจน์ไม่ได้ มันจะบอกว่า
**"ลองแล้ว แต่ยังพิสูจน์ไม่ได้ — เพราะเหตุนี้"** แทนที่จะอ้างว่าสำเร็จเงียบๆ ฟังดูแย่กว่า
แต่จริงๆ ดีกว่ามหาศาล เพราะคุณจะรู้ทันทีว่าส่วนไหนเชื่อได้บ้าง

**มันปฏิเสธเป็น** ถามว่าควรสร้างสิ่งนี้ไหม มันมีสิทธิ์ตอบว่า *อย่าทำ* พร้อมเขียนเหตุผลไว้
เพื่อที่เดือนหน้าจะได้ไม่ต้องมาเถียงกันใหม่

**มันจำได้** `/nzs-learn` บันทึกสิ่งที่ได้ผล และที่มีประโยชน์กว่าคือ *รูปแบบ* ของความผิดพลาด
ไม่ใช่ "แก้บรรทัด 40 แล้วพลาด" แต่เป็น "การ find-and-replace ที่คำเป้าหมายถูกเปลี่ยนไปแล้ว"
รูปแบบคือสิ่งที่เดือนหน้าคุณจะจำได้ในไฟล์อื่น เหตุการณ์เดี่ยวๆ สอนอะไรไม่ได้ แต่รูปแบบสอนได้หมด

## คำสั่งที่คุณจะได้ใช้จริง

ที่เหลือ AI หยิบใช้เองอัตโนมัติ คุณจำแค่นี้พอ

| พิมพ์ | เมื่อไหร่ |
|---|---|
| `/nzs-start` | **ทุกครั้งที่ไม่แน่ใจ** มันวางแผนให้ว่าจะใช้อะไรบ้าง |
| `/nzs-roundtable` | มีไอเดียลอยๆ หรืออยากโดนเถียง — ตั้งคนนอกมีอคติ, CTO, senior ตัดสิน ไม่ต้องรอคุณ |
| `/nzs-learn` | เพิ่งมีอะไรได้ผล หรือเพิ่งพัง แล้วอยากให้จำไว้ |
| `/nzs-handoff` | บริบทจะหมด หรือจะหยุดทำวันนี้แล้ว |

ยังมี `/nzs-setup` สำหรับเครื่องใหม่ และ `/nzs-goal` สำหรับงานที่ใหญ่เกินนั่งเดียว

## นิสัยเดียวที่ควรขโมยไปใช้

ถึงคุณจะไม่ติดตั้งอะไรเลย ก็เอาข้อนี้ไป:

**พอ AI บอกว่าเสร็จแล้ว ให้ถามว่า "ขอดูหน่อย"**

ไม่ใช่ถามว่า "แน่ใจนะ" — มันตอบว่าแน่ใจอยู่แล้ว แต่ให้ขอ *หลักฐาน*: คำสั่งที่รันกับสิ่งที่มัน
พิมพ์ออกมา, ภาพหน้าจอ, แถวข้อมูลจากฐานข้อมูล, HTTP response จริงๆ ถ้ามันเอาพวกนี้มาให้
ไม่ได้ แปลว่างานยังไม่เสร็จ แค่ถูกบรรยายไว้เฉยๆ

คำถามเดียวนี้คือคุณค่าส่วนใหญ่ของทั้งรีโป ส่วนรีโปคือคำถามนั้นที่เขียนไว้เป็นลายลักษณ์อักษร
เพื่อให้ AI ถามตัวเองก่อนที่คุณจะต้องถาม

## ถ้ามันไม่ทำงาน

**พิมพ์ `/` แล้วไม่เห็น `nzs-start`**
เกือบทุกครั้งคือ session ยังไม่ได้โหลดใหม่ Claude Code อ่านรายการ skill, plugin และ MCP
**ตอนเปิด session** เพราะงั้นอะไรที่ติดตั้งระหว่างทางจะอยู่บนดิสก์แต่ยังไม่ถูกโหลด
สั่ง `/reload-plugins` ก่อน ถ้ายังไม่ขึ้นให้ **restart Claude Code** — MCP server ที่เพิ่ง
เชื่อมต่อใหม่ต้อง restart เสมอ จากนั้นสั่ง `/plugin` ดูว่ามี `nzs-skills` อยู่ไหม ถ้าคุณก๊อปไฟล์เอง ไฟล์ต้องอยู่ใน `~/.claude/skills/` หรือ `.claude/skills/`
หนึ่งโฟลเดอร์ต่อหนึ่ง skill และข้างในต้องมี `SKILL.md`

**มันถามหา `.method/config.yml`**
ปกติของการใช้ครั้งแรก ไฟล์นั้นบันทึกว่า *โปรเจกต์ของคุณ* ใช้อะไร — คำสั่งเทสต์, ฐานข้อมูล,
เบราว์เซอร์ ปล่อยให้ `method-onboard` เขียนให้ มันถามไม่เกินหกคำถาม ที่เหลือมันดูจากไฟล์
ในโปรเจกต์เอง นี่คือเหตุผลที่ไม่มี skill ไหนในนี้ฮาร์ดโค้ดชื่อ framework หรือฐานข้อมูล —
ทุกตัวอ่านจากไฟล์นั้น

**มันชอบบอกว่า "ลองแล้ว แต่ยังพิสูจน์ไม่ได้"**
ทำงานถูกต้องแล้ว และมันกำลังบอกอะไรบางอย่างที่เป็นจริง: มันเอื้อมไม่ถึงสิ่งที่จะใช้ตัดสิน
คำอ้างนั้น ส่วนใหญ่คือ dev server ไม่ได้รันอยู่ หรือเครื่องมือเบราว์เซอร์ยังไม่เชื่อมต่อ
แก้ตรงนั้นแล้วการตรวจอันเดิมจะพิสูจน์ได้เอง

**มันปฏิเสธไม่ทำสิ่งที่ผมสั่ง**
ทุก skill ประกาศไว้ว่าจะไม่ทำอะไรบ้าง และการปฏิเสธพวกนั้นตั้งใจใส่ไว้ — มันคือส่วนที่ทำให้
ส่วนที่เหลือเชื่อถือได้ ถ้าการปฏิเสธนั้นไม่เหมาะกับสถานการณ์ของคุณ บอกไปได้เลยแล้วมันจะทำต่อ
คนตัดสินใจคือคุณ แต่อ่านเหตุผลก่อน เพราะส่วนใหญ่มันคือบทเรียนราคาถูกของสิ่งที่มีคนจ่ายแพง
ไปแล้ว

**รู้สึกว่ามันช้า**
ช้าจริง และตั้งใจให้ช้าในตอนต้น การตรวจกินเวลาตอนแรก แต่ช่วยประหยัดทั้งบ่ายที่คุณต้องมานั่ง
รื้อของที่พังเงียบๆ มาตลอด ถ้างานไหนทิ้งขว้างจริงๆ และอยากได้เร็ว ก็ไม่ต้องใช้ตัวนี้ —
นั่นเป็นทางเลือกที่ชอบธรรม และเป็นสิทธิ์ของคุณ

# ระบบนิเวศทั้งหมด

[English](ECOSYSTEM.md) · **ภาษาไทย**

skills ในรีโปนี้คือ **วิธีทำงาน** แต่วิธีทำงานต้องมี **ความสามารถ** มารองรับ — บางอย่างต้อง
อ่านฐานข้อมูลได้จริง ขับเบราว์เซอร์ได้จริง ทำดัชนีโค้ดได้ หรือจำสัปดาห์ที่แล้วได้ หน้านี้คือ
อีกครึ่งที่เหลือ: เครื่องมือทุกตัวที่ใช้ร่วมกัน มันคืออะไร ได้อะไร ใช้ยังไง และพังตรงไหน

อ่านรอบเดียวพอ หลังจากนั้นให้ `nzs-start` จัด stack ให้

---

## ภาพรวมทั้งหมด สรุปด้วยประโยคเดียว

> **skill เป็นตัวตัดสินว่าอะไรนับเป็นหลักฐาน ส่วน tool คือวิธีที่คุณไปเอาหลักฐานนั้นมา**

`method-verify` บอกว่าคำอ้างเรื่องการแสดงผลต้องพิสูจน์ที่ DOM แต่มันเปิดเบราว์เซอร์เองไม่ได้ —
Playwright ทำ `method-security` บอกว่าคำอ้างเรื่องขอบเขตข้อมูลต้องพิสูจน์ด้วยการอ่านแถวจริง
แต่มันไม่รู้จักฐานข้อมูลคุณ — client ของคุณรู้ `nzs-learn` บอกว่าบทเรียนต้องอยู่รอดข้าม session
แต่มันเก็บอะไรเองไม่ได้ — engram เก็บ

การแยกแบบนี้ตั้งใจ ถ้า skill ระบุชื่อ browser driver ตรงๆ วันที่คุณเปลี่ยน driver มันก็ใช้ไม่ได้
ทันที เพราะงั้นแต่ละโปรเจกต์เขียน `.method/config.yml` ครั้งเดียว (ด้วย `method-onboard`)
แล้วทุก skill อ่านจากไฟล์นั้น

```
        คุณ ── /nzs-start ──▶ stack ของ skills            ← วิธีทำงาน (รีโปนี้)
                              │
                              ▼
                    .method/config.yml                  ← โปรเจกต์นี้ใช้อะไร
                              │
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
   ความสามารถ           ความจำ + บริบท          เครื่องมือรีวิว
   playwright            engram, headroom        codex, bug-hunter,
   codegraph             CLAUDE.md               scrutinize, impeccable
   context7              handoff.md              debug-mantra
   db client ของคุณ
```

## ชั้นที่ 1 — ความสามารถ: พิสูจน์คำอ้างยังไง

พวกนี้คือเหตุผลที่ `method-verify` ปฏิเสธรายงานเปล่าๆ แล้วเรียกร้องหลักฐานได้

### Playwright MCP — สื่อสำหรับทุกอย่างที่แสดงผล

**คืออะไร** เบราว์เซอร์ที่ Claude ขับได้: เปิดหน้า คลิก พิมพ์ ถ่ายภาพ อ่าน DOM จริง รัน
JavaScript ในหน้า ดู network request

**ได้อะไร** เป็นคำตอบเดียวที่ซื่อสัตย์ต่อคำถาม "มันแสดงผลจริงไหม" อ่าน JSX ได้แค่ *เจตนา*
อ่าน DOM ถึงจะได้ *ข้อเท็จจริง* ตัวนี้ถูกใช้บ่อยที่สุดในวิธีนี้ เพราะคำอ้างเกี่ยวกับ UI ส่วนใหญ่
เป็นเรื่องโกหกจนกว่าจะวัด

```js
// คำอ้างเรื่องสไตล์ — พิสูจน์ที่ค่าที่คำนวณแล้ว ไม่ใช่ที่ source
getComputedStyle(el).outlineColor      // → "lab(45.13 18.36 -71.70)"
// คำอ้างเชิงโครงสร้าง — ตัว probe คือหลักฐาน
document.querySelectorAll("form form").length   // → 1 พิสูจน์ว่ามี form ซ้อน form
```

**กับดักที่โดนมาแล้วจริง** dev server เสิร์ฟ **CSS chunk เก่าค้าง** ได้ เคยมีเคสที่ token ถูกต้อง
ใน source แต่เบราว์เซอร์บอกว่าไม่ถูกใช้ — และเบราว์เซอร์พูดถูกเกี่ยวกับโค้ดที่กำลังรันอยู่จริง
มันเสิร์ฟของเก่า ก่อนเชื่อผลลบ ให้บังคับ rebuild ก่อน

อีกอัน: locator แบบ strict ที่แมตช์หลายตัวจะ **throw** และ throw แปลว่า *สรุปไม่ได้*
ไม่ใช่ "ไม่เจอ" ให้เจาะ selector ให้แคบลงแล้วอ่านใหม่

### CodeGraph — กราฟสัญลักษณ์แทนการ grep

**คืออะไร** กราฟ SQLite ของโค้ดเบส: สัญลักษณ์ เส้นเรียก ไฟล์ สั่ง
`codegraph explore "<คำถามหรือชื่อสัญลักษณ์>"` แล้วได้ source จริงพร้อมเลขบรรทัด **บวกกับ
เส้นทางการเรียกระหว่างกัน** ในรอบเดียว

**ได้อะไร** มันตาม dynamic dispatch ได้ ซึ่ง grep ทำไม่ได้เชิงโครงสร้าง ตอน `method-security`
ถามว่า *"public request path เอื้อมถึง service-role client ได้ไหม"* — นั่นคือคำถามเรื่อง
เส้นทางการเรียก ซึ่งกราฟตอบได้ ส่วนการค้นข้อความได้แค่เดา

```bash
codegraph init                       # ทำดัชนีทั้งรีโป — ต้องถามก่อน ไม่ฟรี
codegraph explore "AiDraftForm"      # source + ใครเรียก + รัศมีผลกระทบ
```

**กฎ** ห้ามรัน `codegraph init` โดยไม่ถาม ถ้าไม่มีโฟลเดอร์ `.codegraph/` แปลว่าโปรเจกต์นั้น
ยังไม่เลือกใช้ ให้ใช้ Read กับ Grep ไปตามปกติ อย่าไปสร้างเงียบๆ

### Context7 MCP — เอกสารไลบรารีเวอร์ชันปัจจุบัน

**คืออะไร** เอกสารที่ตรงเวอร์ชันของไลบรารี framework SDK และ CLI ดึงมาตอนต้องใช้

**ได้อะไร** ข้อมูลที่โมเดลเรียนมามีวันตัด แต่ framework ไม่หยุดพัฒนา `method-research` กับ
`method-plan` ใช้ตัวนี้เพื่อให้แผนอ้าง API ที่มีอยู่จริงวันนี้ ไม่ใช่ API ที่โมเดลจำได้ ใช้แทน
web search สำหรับทุกอย่างที่เป็นเรื่องไลบรารี

**ไม่ต้องใช้ตอนไหน** ตรรกะทางธุรกิจ การ refactor คำถามการเขียนโปรแกรมทั่วไป มันตอบว่า
"API คืออะไร" ไม่ได้ตอบว่า "ควรสร้างอะไร"

### 9Router — endpoint เดียวแบบ OpenAI สำหรับหลายผู้ให้บริการ

**คืออะไร** เกตเวย์ที่เปิด `/v1/...` สำหรับ chat, รูป, TTS, embedding, web search และ vision
พร้อมสลับบัญชีอัตโนมัติเมื่อเจ๊ง ดูรุ่นที่ใช้ได้จาก `/v1/models/image`, `/v1/models` แล้วเอา
`id` ที่ได้ไปใส่เป็น `model`

**ได้อะไร** ไม่ผูกกับผู้ให้บริการรายเดียว และใช้คีย์เดียว เป็นตัวที่ `method-design` หยิบใช้เวลา
ต้องการภาพ และเป็นตัวที่ `method-cost` ชี้ ledger ไปหาได้

```bash
curl -X POST "$NINEROUTER_URL/v1/images/generations?response_format=binary" \
  -H "Authorization: Bearer $NINEROUTER_KEY" -H "Content-Type: application/json" \
  -d '{"model":"cx/gpt-5.5-image","prompt":"…","size":"1536x640"}' --output out.png
```

**กับดักสองข้อ เจอมาทั้งคู่ตอนทำรูปให้รีโปนี้** รุ่นหนึ่งตอบ **429 quota exceeded** ขณะที่
รุ่นพี่น้องยังทำงานปกติ — ให้ probe ถูกๆ ก่อน แล้วค่อยถอยไปรุ่นอื่น ซึ่งตรงกับกฎการลดระดับ
ของ `method-harden` พอดี และ **`size` เป็นแค่คำใบ้** สองรุ่นเมินมันแล้วส่งภาพแนวตั้งกลับมา
ถ้าอัตราส่วนสำคัญ ให้เขียนย้ำใน prompt ด้วย แล้ว *ดูผลจริง* — สื่อเดียวที่ตัดสินคำอ้างเรื่องรูป
ได้คือตาคุณเอง

## ชั้นที่ 2 — ความจำและบริบท: ทำให้งานอยู่รอด

### engram MCP — ความจำข้าม session

**คืออะไร** ความจำถาวรที่ค้นได้ `mem_save` เขียนสิ่งที่สังเกตได้ `mem_search` หาเจอสัปดาห์หน้า
`mem_context` กู้ประวัติล่าสุดคืนหลังโดนบีบอัดบริบท

**ได้อะไร** เป็นตัวแยกระหว่างวิธีทำงานที่ *เก่งขึ้นเรื่อยๆ* กับวิธีที่วนผิดซ้ำเดิม `nzs-learn`
เขียนลงไปสี่แบบ: ของที่ได้ผลพร้อมเทคนิคที่ชนะทางเลือกที่ชัดเจนกว่า, ความผิดพลาดที่บันทึก
**ตามรูปแบบ** พร้อมวิธีกันซ้ำ, รสนิยมของคุณด้วยคำของคุณเอง, และข้อเท็จจริงเรื่องขั้นตอน
ทำงานที่ประหยัดเวลาจริง

**ทำไม "ตามรูปแบบ" ถึงสำคัญที่สุด** *"แก้ไฟล์แล้วไม่แมตช์อะไรเลย"* เป็นแค่เหตุการณ์ สอนอะไร
ไม่ได้ แต่ *"การ find-and-replace ที่คำเป้าหมายถูกเปลี่ยนไปแล้วก่อนหน้านี้"* คือรูปแบบ และ
รูปแบบคือสิ่งที่จำได้ในไฟล์อื่นเดือนหน้า โปรเจกต์นี้ทำพลาดแบบนั้นสามครั้งก่อนจะมีใครตั้งชื่อมัน
พอตั้งชื่อได้ มันก็หยุด

**กฎความซื่อสัตย์** ถ้า engram ไม่ได้เชื่อมต่อ `nzs-learn` ต้องบอกตรงๆ แล้วเขียนไฟล์ในเครื่อง
แทน — **และบอกให้ดัง** ความจำที่ผู้ใช้คิดว่าถาวรแต่จริงๆ ไม่ถาวร แย่กว่าไม่มีความจำเลย

### headroom MCP — บีบอัดบริบท

**คืออะไร** `headroom_compress` กับ `headroom_retrieve` ย้ายของหนักออกจากหน้าต่างทำงาน
แล้วดึงกลับมาตอนต้องใช้ `headroom_stats` บอกสถานะ

**ได้อะไร** ทำให้รันยาวๆ ได้ กฎเศรษฐศาสตร์โทเคนของ `nzs-goal` — *"ถ้าขั้นตอนไหนจะยัดของ
เกินหนึ่งหน้าจอเข้าหน้าต่างหลัก ขั้นตอนนั้นต้องเป็น subagent"* — คือนโยบาย ส่วน headroom
คือกลไกหนึ่งที่ทำให้นโยบายนั้นจ่ายไหว

### `handoff.md` + `nzs-handoff` — ส่งต่อระหว่าง session

**คืออะไร** ไฟล์ธรรมดาที่ root ของรีโป ชื่อกำหนดใน `config.handoff`

**ได้อะไร** session ถัดไปเริ่มตรงที่อันนี้จบ ไม่ต้องไล่คิดใหม่ กฎที่ทำให้มันได้ผลจริงมีสามข้อ
และตั้งใจให้แปลก: ทุก "เสร็จแล้ว" ต้องมีหลักฐานติดมาด้วย ไม่งั้นย้ายไปช่อง "กำลังทำ";
มี next action **ข้อเดียว** เพราะรายการห้าข้อจะโดนจัดลำดับใหม่ตั้งแต่ต้นอยู่ดี ซึ่งก็คืองานที่
มันควรจะช่วยประหยัด; และแนวทางที่ลองแล้วไม่เวิร์ก **บังคับต้องเขียน** เพราะถ้าไม่เขียน
session หน้าจะจ่ายค่าทางตันเดิมซ้ำอีกรอบ

## ชั้นที่ 3 — เครื่องมือรีวิว

![verified and refuted](assets/verified-refuted.png)

`method-review` หมุนบทบาท และพวกนี้คือเครื่องมือที่สวมบทบาทนั้น กฎที่ทำให้การหมุนได้ผล:
**ห้ามใช้บทบาทซ้ำจนกว่าจะครบทุกบทบาท** เพราะบทบาทเดิมจะเจอปัญหาชนิดเดิม แล้วเข้าใจว่า
นั่นคือความคืบหน้า

| เครื่องมือ | บทบาทที่สวม | สิ่งที่มันพลาดไม่ได้เชิงโครงสร้าง |
|---|---|---|
| **bug-hunter** | Recon → Hunter → Skeptic → Referee พร้อมสายพานแก้ | บั๊กเชิงพฤติกรรม และ false positive — ขั้น Skeptic มีไว้ฆ่าพวกนี้ |
| **scrutinize** | คนนอก มองตลอดเส้นทาง "สิ่งนี้ควรมีอยู่ไหม" | ขอบเขตงานที่ไม่เคยมีใครให้เหตุผล ทางที่ง่ายกว่าที่ไม่มีใครตีราคา |
| **debug-mantra** | ทำซ้ำ → หาเส้นทางพัง → พยายามหักล้าง → ไล่ทุกร่องรอย | การเสนอวิธีแก้ก่อนที่จะทำบั๊กซ้ำได้ |
| **impeccable** | ผู้กำกับงานออกแบบระดับรางวัล | งานฝีมือ: ลำดับชั้น จังหวะ ความยับยั้งชั่งใจ พื้นคุณภาพ |
| **codex** (OpenAI) | โมเดลคนละตัวจริงๆ | จุดบอดของโมเดลเดียว — ใกล้เคียงพยานภายนอกที่สุดที่วิธีนี้มี |

**เชื่อมกับรีโปนี้ยังไง** `method-review` เลือกชุดบทบาท และเปิดรอบใหม่ด้วยการตรวจซ้ำว่า
ของที่รอบก่อน *บอกว่าแก้แล้ว* ลงจริงหรือเปล่า เพราะโปรเจกต์นี้บันทึกไว้ว่ามีสามรอบแยกกัน
ที่จับได้ว่าการแก้ถูกรายงานว่าเสร็จทั้งที่ไม่เคยลง ส่วน `method-security`, `method-web-security`
และ `method-ai-security` คือวินัยที่บทบาท `security` อ่าน

**debug-mantra ควรพูดถึงแยก** เพราะเป็นวินัยที่ `method-debug` ถอดมา: *ห้ามเสนอวิธีแก้ก่อน
ทำบั๊กซ้ำได้อย่างเสถียร และให้รันการหักล้างก่อนการพิสูจน์* โปรเจกต์นี้เคย "แก้" focus ring ด้วย
การเปลี่ยน token แล้ววัดได้ 1.97:1 ทั้งที่ต้องการ 3:1 กว่าจะเจอต้นเหตุจริง (ตัวคูณความทึบ)
ก็ต่อเมื่อทำตามลำดับนี้

## ชั้นที่ 4 — ผลลัพธ์และขั้นตอนทำงาน

### caveman — บีบอัดคำตอบ

ตัดคำนำหน้านาม คำฟุ่มเฟือย และการพูดอ้อม แต่เก็บข้อเท็จจริงทางเทคนิคครบ สั่งด้วย `/caveman
lite|full|ultra` **โค้ด commit และข้อความเรื่องความปลอดภัยเขียนปกติ** เพราะการบีบอัดมีไว้ใช้
กับร้อยแก้ว และความกำกวมไม่เคยเป็นการประหยัดที่ยอมรับได้

### rtk — พร็อกซี CLI ที่ฆ่าโทเคน

เขียนคำสั่ง CLI ทั่วไปใหม่ให้กรองผลลัพธ์ ลดโทเคนที่ `git status` ดิบหรือ log การ build จะกิน
ไป 60–90% ดูผลประหยัดด้วย `rtk gain`

**กับดักที่ `nzs-setup` ตรวจให้** มีแพ็กเกจ *อีกตัว* ชื่อ `rtk` (Rust type kit) ที่ตอบ `--version`
ได้สวยงามแต่ `gain` พัง ถ้าตรวจด้วย `--version` อย่างเดียว จะรายงานว่าติดตั้งสำเร็จทั้งที่ได้
ซอฟต์แวร์ผิดตัว ต้องตอบได้ทั้งสองคำสั่ง

### superpowers — วินัยว่ากระบวนการมาก่อน

กำหนดว่า skill เชิงกระบวนการต้องรัน *ก่อน* skill เชิงลงมือ: ระดมความคิดก่อนวางแผน,
ดีบักอย่างเป็นระบบก่อนแก้เฉพาะจุด เข้ากันได้กับชุดนี้โดยการออกแบบ — `nzs-start` อยู่ตำแหน่ง
เดียวกันสำหรับ skills ของวิธีนี้เอง

### fable modes — จัดระดับโมเดลตอน spawn

`fable-opus` / `fable-sonnet` / `fable-haiku` จับคู่งานกับความสามารถของโมเดล
`config.models` บันทึกแนวคิดเดียวกันแบบ **อิงความสามารถ ไม่อิงยี่ห้อ** — architect, builder,
mechanical, reviewer — เพื่อให้ config รอดตอนโมเดลเปลี่ยนชื่อ

**กับดักจริง** codex agent ในสภาพแวดล้อมนี้ **ย้ายตัวเองไปทำงานเบื้องหลัง ไม่ตอบกลับทันที**
ถ้ารอมันคือค้างตลอดกาล ที่หนักกว่านั้น: เคยมี agent วางแผนสามตัวติดกันส่งบทสรุปที่ฟังดูมั่นใจ
กลับมา ทั้งที่เรียกเครื่องมือ **ศูนย์ครั้ง** และไม่ได้เขียนไฟล์เลย จับได้เพราะไปไล่ดูว่าไฟล์มีจริงไหม
ไม่ใช่เพราะอ่านรายงาน นี่คือเหตุผลที่ Ledger ของ `nzs-goal` ถูกเขียนโดยตัว loop จากหลักฐาน
ที่มันเห็นเอง ไม่ใช่โดย agent ที่อ้างว่าทำงานแล้ว

## ท่าที่ควรจำ

ตั้งชื่อไว้ให้เรียกใช้ได้เลย

**1. อ่านแบบคนนอก** — `scrutinize` → `method-decide`
ใช้ก่อนสร้างอะไรที่ใหญ่หน่อย ให้คนนอกถามรอบเดียวว่าสิ่งนี้ควรมีอยู่ไหม แล้วบันทึกการตัดสินใจ
พร้อมข้อสมมติ เป็นวิธีถูกที่สุดที่จะไม่สร้างของผิด

**2. เก็บข้อมูลก่อนสร้าง** — `method-research` → `method-extract` → `method-plan` → `method-code`
การเก็บข้อมูลรัน **ก่อนเสมอ** ห้ามวางแผนจากอ้างอิงดิบ ให้สกัดเป็นกฎก่อน แล้วค่อยวางแผนกับกฎ
ถ้าอ้างอิงเป็นเว็บจริง ใช้ `method-clone` แทนสองตัวแรก

**3. การหมุน** — `method-review` × 3 หมุนบทบาท แล้วปิดด้วย `method-verify`
รอบแรกไม่ต้องตรวจซ้ำ (ยังไม่มีอะไรให้ตรวจ) รอบ 2 และ 3 เปิดด้วยการตรวจว่าของที่รอบก่อนแก้
ลงจริงไหม ออกเมื่อบทบาทหมด ไม่ใช่เมื่อรู้สึกว่าพอแล้ว

**4. การล่า** — `bug-hunter --fix` → `debug-mantra` กับอะไรที่มันอธิบายไม่ได้ → `method-guard` กับอะไรที่ซ้ำ
ขั้นที่สามคือขั้นที่คนข้าม และเป็นขั้นที่ทบต้น: บั๊กชนิดที่โผล่มาสองครั้งได้ guard ถาวร

**5. รันยาว** — `nzs-goal` → `/goal` + `/loop` ร่วมกับ headroom และ subagent
สำหรับงานที่ใหญ่เกินหนึ่งหน้าต่าง พรอมต์คงที่ ไฟล์แผนเปลี่ยน หยุดเมื่อ `## Open` ว่าง **หรือ**
สองรอบติดที่ไม่มีแถว Ledger เปลี่ยนเลย — loop ที่แสดงความคืบหน้าไม่ได้ แปลว่าไม่มีความคืบหน้า

**6. ส่งขึ้นจริง** — `method-verify` → `method-ship`
ตรวจ schema ของ production **ก่อน** push ที่ต้องพึ่งมัน ไม่ใช่หลัง

**7. ปิด session** — `nzs-learn` แล้วค่อย `nzs-handoff`
เรียนรู้ก่อนตอนความเข้าใจยังคม แล้วค่อยส่งต่อเมื่อไม่เหลืออะไรให้บันทึก

## Use case ตั้งแต่ต้นจนจบ

**"ทำหน้าเราให้เหมือนของเขา"**
`method-clone` (เก็บอ้างอิง โดยให้ Playwright วัดค่าที่คำนวณจริง) → `method-extract`
(ได้กฎพร้อมเหตุผล ไม่ใช่ภาพหน้าจอ) → `method-plan` → สร้าง → `method-design` +
`impeccable` → `method-review` ด้วยบทบาท `design-jury`
ขั้นวัดห้ามข้าม: เคยกะด้วยตาว่า "ประมาณ 510px" แล้วผิดไป 73px มีแต่การวัดที่บอกได้

**"ฟีเจอร์นี้คุ้มที่จะทำไหม"**
`nzs-grill` ถ้าโจทย์ยังคลุมเครือ → `method-discovery` (ข้อสมมติจริงไหม) → `method-decide`
→ `method-cost` ถ้ามีค่าใช้จ่ายต่อครั้ง ผลลัพธ์ที่บอกว่า *อย่าทำ* คือความสำเร็จ และถูก
บันทึกพร้อมราคาไว้ ไม่ต้องมีใครมานั่งคิดใหม่

**"รีวิว PR นี้ให้ดีๆ"**
`method-review` เลือกชุดบทบาทตามชนิดของการเปลี่ยนแปลง ถ้าเป็น endpoint ก็ `security`
(อ่าน `method-security` + `method-web-security`), `edge-case`, แล้ว `bug-hunter` ผลที่เจอถูกจัดเป็น
แก้เดี๋ยวนี้ / บันทึกพร้อมราคา / ถอนพร้อมเหตุผล — ไม่มีการเงียบหาย

**"มีอะไรพัง ไม่มีใครรู้ว่าทำไม"**
`method-debug` / `debug-mantra` ทำซ้ำให้ได้ก่อน ไม่มี repro ห้ามตั้งสมมติฐาน แล้วค่อยไล่ knob
แล้วค่อยฝังเครื่องมือวัด เก็บ ledger ไว้: สมมติฐานใหม่ต้องอธิบาย **ทุก** ร่องรอยก่อนหน้าได้
ไม่ใช่แค่อันล่าสุด

**"เราจะใส่ AI เข้าไปในโปรดักต์"**
`method-threat` ก่อน → `method-ai-security` สำหรับเรื่อง injection กับปลายทางของ output →
`method-cost` สำหรับเพดานค่าใช้จ่าย → `method-guard` สำหรับตัวคุมงบ
output ของโมเดลคือ input ที่เชื่อไม่ได้ และปลายทางที่มันไปลงเป็นตัวกำหนดว่ามันทำอะไรได้

**"ติดตั้งเครื่องใหม่ / workspace ใหม่"**
`nzs-setup` มันติดตั้งแล้ว *พิสูจน์* ทีละตัว อะไรที่ตรวจไม่ได้จะรายงานว่า **ยังไม่ได้พิสูจน์**
ไม่ใช่ว่าเสร็จ

**"บริบทจะหมดแล้ว"**
`nzs-learn` → `nzs-handoff`

## กรณีศึกษา — เรื่องที่เกิดขึ้นจริง

พวกนี้คือเหตุผลที่กฎแต่ละข้อมีอยู่ ทุกข้อจ่ายด้วยเงินจริงหรือเวลาจริง

**ช่องที่ไม่เคยทำงานถูกเลยสักครั้ง** ตัวแยก URL ตัดด้วยตัวอักษร `s` เพราะ backslash หายไป
หนึ่งตัวใน regex มันอยู่บน production เงียบๆ ตลอดอายุของมัน ไม่มีใครเห็นเพราะอาการดูเหมือน
เว็บปลายทางพัง ไม่ใช่ตัวแยกพัง *กฎ: การแก้ที่ไม่แมตช์อะไรเลย กับ probe ที่แมตช์กว้างเกินไป
คือความผิดพลาดเดียวกัน*

**เจ็ด commit ตกแต่งบนของที่พังอยู่** ดราฟต์ออกมายาว **13% ของเป้า** ขณะที่ commit ปรับ
หน้าจอลงไปอีกเจ็ดครั้งทับข้างบน รีวิวงานฝีมือผ่านหมด — ซึ่งถูกต้องแล้ว เพราะมันไม่ใช่คำถาม
เรื่องงานฝีมือ *กฎ: `method-review` ต้องหมุนบทบาท เพราะบทบาทเดียวมองข้ามตัวเองไม่ได้*

**รอบซ่อมที่ยิงทุกครั้ง** regex ของ guard ตัวหนึ่งตายแบบเดียวกัน ทำให้รอบซ่อมทำงาน **ทุก**
คำขอ จ่ายเงินสองเท่า แล้วทิ้งผล ไม่มีใครเห็นเพราะผลลัพธ์ดูปกติ *กฎ: `method-cost` อ่าน
ledger ไม่ใช่อ่านเจตนา*

**guard ที่สอบตกการทดสอบตอนเกิดของตัวเอง** guard ตรวจความซิงก์ที่เพิ่งเขียนเทียบไบต์ตรงๆ
พอเป็น checkout บน Windows คำสั่ง `git checkout --` คืนไฟล์เป็น CRLF ทำให้ไฟล์ที่
**เหมือนกันทุกประการ** ถูกรายงานว่าต่างกัน จับได้ด้วย mutation test ของตัวมันเอง *กฎ:
`method-guard` — guard ยังเชื่อไม่ได้จนกว่าจะเห็นมันแดงตอนแกล้งทำให้พัง และเขียวตอนคืนค่า*
กับดักเดียวกันนี้เล่นงาน validator ของรีโปนี้ซ้ำอีก จึงเป็นที่มาของ `.gitattributes` ที่ตรึง `eol=lf`

**router ที่เอื้อมไม่ถึง entry point ของตัวเอง** `nzs-start` — skill ที่มีหน้าที่หา skill ที่ถูกต้อง —
เรียกชื่อ skill ชั้นบนได้แค่ 1 จาก 6 อีกห้าตัวไม่มีคำขอไหนไปถึงได้เลย รีวิวปรปักษ์สามรอบ
มองข้ามมัน เพราะทุกรอบ *ใช้* router แต่ไม่มีรอบไหนถามว่ามันเอื้อมถึงอะไรได้บ้าง *กฎ: วิธีแก้
ไม่ใช่การไปไล่แก้รายการ แต่คือ check ที่รันได้และทำให้ CI แดง*

**ตัวเลขที่ล้าสมัยสามครั้ง** `expect 26` วางข้างคำสั่งที่คืนค่า 29; `29 skills`; `the four entry
points` ทั้งที่มีเจ็ด *กฎ: อย่าเขียนจำนวนนับ ให้เขียนการเปรียบเทียบแทน* ตอนนี้บังคับด้วย
`scripts/validate.mjs`

**คลิกเดียวได้สองดราฟต์** การเปลี่ยน `aria-disabled` ทำให้เกิดปัญหาว่าดับเบิลคลิกแล้วซื้อการ
generate สองครั้ง พิสูจน์ว่าแก้แล้วด้วยการคลิกห้าครั้งแล้วนับ POST ได้ **หนึ่ง** ครั้ง *กฎ:
พิสูจน์ในสื่อของมัน — แท็บ network ไม่ใช่ diff*
